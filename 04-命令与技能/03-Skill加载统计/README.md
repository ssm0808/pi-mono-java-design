## 1. 目标与边界

管理端直接查询哪些 Skill 加载较多，支持累计排名、近 7 天/30 天排名，以及单个 Skill 的逐日趋势。列表请求无需事先知道 Skill ID。只有进入某个 Skill 的趋势详情时才在路径中携带一个 skillId。

计量单位为成功记账的 SKILL.md 全文加载次数。重复完整加载分别计数，显式 Skill 命令受理和同执行 Read 全文覆盖共用这个口径；不等同于任务采用数、模型已接收数、执行成功数或无损审计。这个指标作为本版推荐口径，不能宣称对“业务采用率”的问题已给出答案。

统计库只维护观测过的加载汇总，不复制 Skill 主数据。当前统计范围内次数大于零的 Skill 进入排名；零次 Skill 的完整目录、名称、删除状态和目录权限仍归 CampusMate。无统计记录不能推导 Skill 不存在；也不凭请求 ID 构造一个看似存在的零次资源。

**权限范围。** 本版沿用现有部署级统计模型，面向已授权的部署管理端，不定义跨租户用户可直接调用的公共 API。该范围是待确认的推荐边界：现有元数据主设计明确本期不新增多租户字段，PR 表也没有租户归属。CampusMate/部署入口必须先确认调用方可查看整个统计数据集，再允许访问内部查询；浏览器不直连 Claw。现有 X-HW-ID 是凭据 ID，不能充当 tenantId。租户级接入必须先补可信租户归属及 SQL 范围条件，在汇总、排序、分页之前过滤；不得先分页再过滤，也不得把部署总数当作租户次数。本文不虚构已存在的鉴权适配器或公司内部权限接口。

本期增加两张汇总表及两个 GET 查询操作，不保存逐次加载事件、正文、摘要、Agent、版本、统计执行 UUID。查询不调用模型，不刷新 Agent，不读取 SKILL.md。业务审计沿用原有日志和 Session 权威记录；本专题汇总不能替代它们。

## 2. 计数口径与采集边界

| 场景 | 记账规则 |
|---|---|
| 一次成功完整 Read | 加 1 |
| 同一执行的多次 Read 合起来完整覆盖 | 完成一轮加 1，清空该 Skill 的本轮覆盖进度 |
| 重复或重叠片段但仍缺行 | 不计数 |
| 同一任务再次完整加载 | 再加 1 |
| 显式 Skill 命令 | 完整绑定快照正文输入受理成功后加 1；解析或受理失败不计数 |
| 命令加载后又完整 Read | 各自计数，总计 2 |
| 目录扫描、绑定、校验、prepare/refresh | 不计数 |
| 上下文复用、恢复、重放历史 | 不因恢复再次计数 |
| 记账后模型失败或任务取消 | 不扣减既有计数 |

保留 #298 的 Host 归因：以受管执行快照的 Skill 身份、版本和本次实际字节摘要验证加载证据。Read 保持通用文件读取职责，不依赖 Skill 统计类型或 Mapper。摘要、版本和完整行位图只服务于执行内认定，不成为统计表字段。不同执行、版本、摘要、Agent 的片段不拼接；进程结束丢弃未完成覆盖。

Read 路径在最终后置处理成功、正文未替换、未观察到取消时合并覆盖；显式命令在既有输入受理边界之后记账。统计技术失败允许漏计，不改变已经成功的主流程；不能为了避免漏计而重做命令受理或工具调用。

## 3. 数据库模型

全量安装 DDL：[schema.sql](schema.sql)。以下数据类型、约束与索引以该 SQL 为准。

### 3.1 累计表：t_skill_load_stats

每个 Skill 一行，仅在第一次成功记账时创建。

| 字段 | 类型 | 用途 |
|---|---|---|
| skill_id | VARCHAR(64)，主键 | 沿用 Skill ID 的精确身份，不裁剪或归一大小写 |
| full_load_count | BIGINT，非空且大于 0 | 自本功能启用以来成功记账的累计次数 |
| last_loaded_at | TIMESTAMPTZ(3)，非空 | 最近一次记账采用的数据库事务时间 |

为“次数倒序、Skill ID 升序”和“最近时间倒序、Skill ID 升序”分别建索引。两个索引增加写入维护成本，换取两种累计列表的查询入口；不能据索引存在宣称已达到性能指标。

### 3.2 日表：t_skill_load_daily_stats

每个有加载的 Skill 每个自然日最多一行；没有加载的日期不写零值行。

| 字段 | 类型 | 用途 |
|---|---|---|
| stat_date | DATE，与 skill_id 组成主键 | Asia/Shanghai 自然日 |
| skill_id | VARCHAR(64) | 与累计表使用相同 Skill 身份 |
| full_load_count | BIGINT，非空且大于 0 | 该日成功记账的次数 |
| last_loaded_at | TIMESTAMPTZ(3)，非空 | 该日最近一次记账采用的数据库事务时间 |

主键顺序为 `(stat_date, skill_id)`，便于日期范围聚合及到期清理；另建 `(skill_id, stat_date)` 索引供单 Skill 趋势查询。两表无外键关联远端 Skill 目录，不建立跨服务数据库耦合；累计/日汇总一致性由同库事务保证。

**字段减法的理由。** 统计查询只需身份、数量和时间。逐次 invocation_id/execution_id、Agent、版本、摘要既不参与本版分组，也不提供真实业务任务关联，因此不持久化。将来需要版本分析或逐次追溯时先明确维度、可靠性和保留要求，不能把本版汇总解释为已有这些能力。

### 3.3 时间、保留与删除

- 数据库存储带时区时间，HTTP 时间戳统一输出 UTC 毫秒；统计日固定按 Asia/Shanghai 计算，客户端不能改变时区。数据库与各实例主机默认时区不参与分组。
- 同一次统计事务的 CURRENT_TIMESTAMP 先统一转换为 TIMESTAMPTZ(3)，再用于两表的时间与日期，避免午夜附近精度舍入导致日期不一致。按该毫秒精度事务时间归日，不承诺模型送达时间或事务提交时间。
- “近 7/30 天”包含今天：若统计日为 2026-09-15，近 7 天为 `[2026-09-09, 2026-09-16)`；今天仅累计到查询可见的已提交写入。接口同时返回日期边界与 queriedAt。
- 累计表长期保留；日表推荐保留最近 90 个自然日（含今天）。90 天是本版初始设计值，不是用户额外确认的合规保留期限；覆盖 30 天查询，并留出维护余量。
- 平台每日按数据库日期删除 `stat_date < today - 89 days` 的日记录；使用已有运维调度、专用清理角色和有界批次，不增加 Runtime 内后台清理框架。清理失败告警，数据暂时多留，不影响最近窗口；运行事务需超时，不能悬挂到越过保留边界后再提交旧日计数。
- 清理日表不扣减累计表；累计数不通过保留下来的日表重新计算。删除 Session、取消任务、更新 Skill 版本或解除 Agent 绑定均不重置汇总。Skill 删除后保留匿名标识统计，ID 不得复用于另一 Skill；法定删除或管理员清除须作为已有数据治理操作同时处理两表。
- 本期是首次发布的全量安装，不设计存量迁移、不回填启用前的加载。日数据过期后不承诺可恢复；备份恢复必须以同库一致备份恢复两表，不能只恢复一张。

## 4. 写入事务、并发与失败

[record-load.sql](record-load.sql) 给出目标写入事务。采用主键冲突时的数据库原子 `count + 1`，禁止在 Java 先 SELECT 次数再覆盖写回。所有写入遵循累计表、日表的固定顺序；同一 Skill 热点会发生行锁竞争，不宣称汇总表消除了写入压力。

`SkillLoadRecorder` 调用独立 Spring Bean `SkillLoadStatisticsWriteService.record`，后者开启独立短事务（REQUIRES_NEW），两次 Mapper 更新全部成功才提交。异常离开事务代理完成回滚后，由 Recorder 捕获并记录失败；不能在事务内部吞异常后提交半笔，也不能通过 self-invocation 绕过 Spring 事务代理。已有数据库事务调用该端口时要核对连接占用，本版采集点应在主受理事务完成后调用。

每个合格加载只发起一次记账尝试；覆盖进度先结束本轮，再尝试写入。SQL、死锁、连接错误或提交结果不明都不自动重试，驱动和拦截器也不得自动重放这两条写语句；不在历史恢复时补加。因没有持久化事件身份，本版不提供恰好一次记账。数据库已提交但客户端报错时可能仍计数，两表事务保证一起成功或一起失败；监控的失败次数不能直接当作漏计数。

复用现有数据源，不新增线程池、消息队列或专属连接池。设置有限连接等待、事务/语句与锁等待预算，并验证总等待；仅捕获异常不能保证无延迟。写入会阻塞当前采集线程，这是本版保留的代价。若现有数据源等待不满足统计延迟预算，必须调整隔离方案后再启用，不能把 Mapper 超时当作端到端上限。查询失败返回错误，不伪造空结果或零值。

应用角色需要两表 SELECT/INSERT/UPDATE；日表 DELETE 仅授予平台清理角色。BIGINT 溢出、非法日期或 ID 由数据库约束兜底并整笔回滚，不能截断、归零或部分写入。业务字段无默认计数，首次插入明确写 1。

SQL 方言采用 openGauss 5.0 官方 `ON DUPLICATE KEY UPDATE` 的证据，未把 PostgreSQL 新语法直接当作公司 GaussDB 已支持能力；真实部署版本的语法与并发验证仍是实施验收项，见[SQL 证据](source-evidence.md#3-sql-方言与验证边界)。

## 5. HTTP 查询行为

两项 operation 均进入唯一 Runtime catalog，使用 `/campusclaw-service/v1` 前缀、GET 资源路径、普通 ResultBean 和既有语言规则。精确字段、参数、完整示例、错误、Header 见[统一接口页](../../01-总体架构/01-CampusClaw多Agent运行时/chat-api-review.html#listSkillLoadStatistics)，不另立 `/internal` 或 `/query` 路径层。

### 5.1 统计列表与排名

`listSkillLoadStatistics` 查询累计或近 7/30 天。无需 skillIds，也不提供另一个可选 ID 数组；先筛选统计范围、聚合，再统一排序，最后分页。默认按次数倒序，支持按最近加载时间倒序；相同值按 Skill ID 升序。复用现有整数 page/limit，缺省和范围由 Service 统一归一，未指定默认值不放在 request VO 字段初始值中。

累计查询直接读累计表；近 7/30 天对日表按 Skill SUM 次数、MAX 最近时间。筛选范围内没有正计数的 Skill 不进入结果。取 limit+1 判定 nextPage，不额外维护 total；空库和合法超范围页返回 200、空 items、nextPage=null。

一条 SQL 同时确定数据库日期、queriedAt 和当前页数据，limit+1 的观察与当前页保持同一语句快照；分页跨请求是实时列表，不固定快照。新加载可能改变排名，跨页可出现重复或遗漏；客户端改变 period/sort/limit 时从第一页重查，刷新时替换当前页，不能把翻完各页视为稳定导出。

### 5.2 单 Skill 日趋势

`getSkillLoadDailyStatistics` 用路径 skillId 查询近 7/30 天，默认近 7 天。先在同一 SQL 快照检查累计统计资源，再用日期序列左连接日表，按日期升序补齐所有日期；不存在日行的日期显示零。

- 累计表存在该 Skill：返回连续 7/30 个日期，可全部为零；例如仅在两个月前加载过的 Skill。
- 累计表没有该 Skill：返回 404 SKILL_LOAD_STATISTICS_NOT_FOUND，含义仅为尚无该 Skill 的加载统计，不能断言 Skill 主数据不存在。
- Skill ID 格式不合法：400；数据库故障：错误响应，不能走 404 或零值分支。

趋势的 fullLoadCount 是同一 SQL 快照中每日值之和，lastLoadedAt 是该窗口内最近时间，没有窗口内记录时为 null。内部按实际业务日期生成 7/30 个日期；不靠 JVM 默认时区、不按固定 24 小时毫秒数切日期。

### 5.3 服务与数据对象

Web 只接收 `SkillLoadStatisticsListRequestVO` / `SkillLoadDailyStatisticsRequestVO` 和路径参数，返回各自独立 `*ResponseVO`；Jakarta 校验放请求 VO/标量边界，默认值、窗口归一和跨字段规则放查询 Service。Mapper 只交互 DTO，不穿透 Controller。SQL 排序通过固定枚举选择 Mapper 分支，不把客户端 sort 文本拼到 SQL。

精确列表和趋势对象共用必要的只读项 VO，遵守既有 Java 中文 Javadoc、版权、DTO/VO、Lombok 和 50 行方法规则。表内不保留响应专用字段，响应也不暴露数据库内部对象。

当前 PR 实现仍是事件表和必传 ID 的 POST；本设计未修改实现仓，也不代表两项 GET 已运行。首次发布直接在实现分支调整完整安装脚本及当前调用者，不保留未发布旧入口作兼容别名；不自动清空任何实际数据库。

不新增 Maven 直接依赖；复用 JDK、已有 Spring 事务、Jakarta Validation、MyBatis Starter 3.0.4、Jackson 和日志组件。没有新依赖的传递图需要披露；部署版本和连接参数仍需在实现中核对，不以“复用已有”免除事务验证。

## 8. 代价、容量与验证边界

累计行数随曾加载的 Skill 数增长；日行数随保留窗口内的活跃 Skill 与日期组合增长，而非随每次加载增长。代价是每次写两张表和索引，同一热门 Skill 的累计行成为并发热点；日查询仍要聚合最多 30 天的候选记录，不能宣称常数时间。

发布验收需用实际 Skill 基数、每日活跃量和同 Skill 并发率验证：写入等待、主流程额外延迟、两种累计排序、近 30 天排名、日清理计划、锁竞争和索引体积。门限由产品延迟预算与部署容量确定，不编造已达标结果。当前完成的是设计和制品校验，GaussDB 集成、运行延迟、执行计划和容量均未实测。

本方案换取直接可查的排名与有界日数据，放弃逐次追溯、任意时分秒切片和数据库内的事件级重放去重。需要这些能力时重新评估事件明细与聚合，不把字段逐个加回当前汇总表。设计制品的实际校验记录见[验证记录](validation.md)。
