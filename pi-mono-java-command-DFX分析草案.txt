Slash Command DFX 分析草案

状态：待确认，不修改设计文档
适用设计：pi-mono Java Command SR 设计
建议插入位置：Command SR 第 14 节后，作为“14.4 DFX 分析”

一、可靠性分析（DFR）

重点设计：

1. CommandInstaller 校验失败时应用不进入 Ready 状态，不允许部分命令目录对外提供服务。
2. CommandCatalogSnapshot 只允许完整发布，运行期不修改静态注册命令。
3. 所有入口，包括聊天框、Command Palette 和按钮，都必须经过同一个 Dispatcher 和 ExecutionGate。
4. Handler 超时、取消、异常后必须释放 Gate；迟到结果不得覆盖最终状态。
5. 有副作用的命令必须由业务服务提供事务、幂等键或补偿机制。
6. /new、/import、/resume、/fork、/clone 等运行时切换必须保持独占和状态一致。
7. SHUTDOWN 阶段停止接收新命令，在关闭期限内等待或取消存量调用。
8. 客户端断开时，不得导致服务端线程、锁或下游连接泄漏；副作用命令超时后的结果应视为“不确定”，不能盲目重试。

验证重点：

- 启动校验失败、重复命令、Handler 缺失；
- Gate 长时间占用、取消、超时和迟到结果；
- 下游不可用、进程关闭、运行时切换失败；
- 重试导致的重复副作用。

二、安全检查（DFS）

重点检查：

1. 前端不能作为权限边界；所有文本调用和结构化调用都必须经过服务端 Parser、Dispatcher、ExecutionGate 和业务授权。
2. 命令名必须来自可信静态目录，禁止客户端提交未注册命令直接执行。
3. 对 rawInput 和 arguments 设置长度、编码、控制字符和资源消耗限制。
4. 不允许 Slash Command 隐式进入 Shell；!、!! 仍按当前设计作为普通 Prompt。
5. Handler 不得直接拼接未授权路径、SQL、URL 或下游命令。
6. 日志、错误消息、诊断输出不得泄露 token、密钥、Cookie、完整会话正文或未脱敏环境变量。
7. 认证、导出、分享、复制、项目可信设置等命令要进行主体、租户、Session 和资源级权限检查。
8. 对高频、昂贵或外部发布类命令增加限流、配额和滥用检测。
9. 命令目录和 Contributor 只允许受信任代码加载，重复命令必须 fail-closed。

安全验证应覆盖参数注入、越权访问、跨租户 Session、敏感信息泄露、伪造结构化调用、重复提交和资源消耗攻击。

三、可服务性分析（DFO）

建议补充以下运维能力：

1. 每次调用生成 invocation_id 和 correlation_id。
2. 统一记录命令名、入口来源、策略、排队耗时、Handler 耗时、结果、错误码、取消原因和目录版本。
3. 指标区分解析、授权、排队、执行、下游调用和输出阶段，不只记录总耗时。
4. 指标标签禁止使用原始参数、用户输入全文、Session 正文或高基数敏感值。
5. Readiness 检查命令目录是否成功发布；Liveness 不应因单个下游短暂故障误报。
6. /doctor 只输出脱敏诊断摘要，并检查目录、Gate、关键依赖和配置。
7. 为 COMMAND_BUSY、COMMAND_TIMEOUT、COMMAND_FAILED、授权拒绝、Gate 等待和目录安装失败建立告警。
8. 维护错误码到用户提示、运维诊断和处理手册的映射。
9. 配置命令超时、最大参数长度、队列上限、限流策略和下游超时时，应在启动时校验。

四、业务安全设计（DFB）

建议按业务风险对命令分级：

风险类别：只读查询
示例：/session、/changelog、/hotkeys、/doctor
必要控制：Session/租户读取权限、脱敏输出、审计

风险类别：状态修改
示例：/model、/settings、/name
必要控制：资源权限、版本校验、并发控制、审计

风险类别：Session 生命周期
示例：/new、/import、/resume、/fork、/clone、/compact
必要控制：独占 Gate、状态转移校验、幂等/补偿、必要时二次确认

风险类别：安全和认证
示例：/login、/logout、/trust
必要控制：最小权限、Step-up 认证、凭证隔离、不可抵赖审计

风险类别：数据外发
示例：/copy、/export、/share
必要控制：数据分级、敏感内容过滤、明确确认、外发审计、失败可追踪

风险类别：应用生命周期
示例：/quit
必要控制：权限控制、停止接收新请求、优雅关闭和未完成任务处理

另外，/skill:<name> 不进入静态 CommandRegistry，应继续遵循 Skill SR 的项目可信、资源加载、fail-open 和动态补全语义。这里需要明确记录：fail-open 是兼容性选择，同时也是业务安全风险，不能误表述为强安全边界。

五、性能设计（DFP）

建议增加以下性能约束：

1. 命令目录使用不可变快照和名称索引，避免每次输入扫描全部命令。
2. Parser 按输入长度线性处理，并限制最大输入和参数大小。
3. 补全使用快照、去抖和请求序号；只展示最新结果，避免旧请求覆盖新结果。
4. Skill 补全只在启动、Reload 或 Session 重新绑定时重建，不在每次键入时扫描文件。
5. SHARED 命令允许并发，EXCLUSIVE 命令使用公平队列；队列必须有上限，禁止无限堆积。
6. 将排队时间、Parser 时间、授权时间、Handler 时间和下游时间分开统计。
7. 等待执行权的时间与 Handler 执行超时分离，但应增加独立的准入等待上限。
8. 对模型、文件、认证、分享和导出等下游调用传递剩余截止时间。
9. 对输出大小、事件数量、并发数和单用户调用频率设置预算。

以下数值可以作为待确认的候选目标，而不是现有契约：

- 本地 Parser + 命令查找 P99 不超过 5 ms；
- 1000 个候选命令的补全 P95 不超过 100 ms；
- 动态 Skill 补全沿用 Skill SR 已提出的 1000 个 Skill、50 ms 目标；
- 队列等待、Handler 执行和下游调用分别统计 P50/P95/P99；
- 性能测试必须覆盖高并发共享命令、独占命令排队、补全竞态和下游慢调用。

六、DFX 闭环

建议把一次 Slash Command 调用统一描述为：

1. 准入：身份、Session、权限、能力和执行策略检查。
2. 执行：Gate 管理并发、取消、超时和生命周期。
3. 结果：返回 HANDLED、REJECTED 或 FAILED，携带稳定错误码和刷新提示。
4. 恢复：通过事务、幂等或补偿处理部分副作用。
5. 观测：日志、指标、审计和诊断使用统一命令身份，但不记录敏感原文。

七、现有文档基线与注意事项

本草案基于当前 Command SR v1.13 的目标架构，重点参考：

- 启动期原子发布不可变命令目录；
- Slash 输入解析和注册命令、Skill Command、普通 Prompt 的路由；
- Dispatcher、ExecutionGate、取消、超时和错误映射；
- 现有安全规则、日志指标和测试策略。

pi 原始 Slash Command 只有名称和说明；CommandExecutionPolicy、取消、超时、并发和统一观测属于 Java 目标架构改造，不应描述为 pi 已有能力。

本草案不修改现有设计文档。确认后再决定是否将其正式写入 Command SR，并同步更新版本历史、测试验收和必要的 PlantUML/验证内容。
