Slash Command DFX 设计概要

状态：待确认
适用设计：pi-mono Java Command SR 设计

一、说明

DFX 用于说明 Slash Command 在异常、安全、运维和高负载场景下应如何工作。

本文使用以下名称：

- 命令解析：从 `/model xxx` 中识别命令名和参数。
- 命令调度：查找对应命令，并调用命令的业务处理逻辑。
- 执行控制：判断命令现在能否运行，并处理并发、取消和超时。

所有聊天框、命令面板和按钮发起的命令，都走同一条处理链路：

用户提交命令
  -> 解析命令
  -> 检查身份、权限和当前状态
  -> 执行命令
  -> 返回结果并记录日志

二、可靠性设计

- 系统启动时一次性检查全部命令。只有全部命令都正确，才对外提供命令能力，避免部分命令可用、部分命令不可用。
- 所有命令由统一的执行控制模块管理，防止两个会修改同一状态的命令同时运行。
- 命令失败、取消或超时后，必须释放占用的锁、线程和连接，不能影响后续命令。
- 已经产生业务影响的命令不能直接重复执行。业务服务应通过事务、幂等或补偿避免重复修改数据。
- Session 切换、上下文压缩和应用关闭等命令，需要独占执行并保证状态完整。

三、安全检查

- 前端只负责提交和展示，不能决定用户是否有权执行命令；权限必须在服务端检查。
- 只有命令目录中已注册的命令才能作为系统命令执行。未知 Slash 输入按照既定路由继续检查 Skill，仍未命中时作为普通 Prompt，不得执行隐藏功能。
- Slash Command 不提供 Shell 执行能力，不能通过命令参数间接执行系统命令。
- 服务端限制命令和参数长度，校验参数格式，避免恶意输入消耗过多内存或计算资源。
- 日志、错误信息和命令输出不得包含密码、Token、Cookie、完整会话内容等敏感信息。
- 所有命令都要验证当前用户、租户、Session 和目标资源之间的关系，防止访问其他用户的数据。

四、可服务性设计

- 每次命令调用生成一个关联 ID。用户看到的错误、服务端日志和监控使用同一个关联 ID，方便定位问题。
- 日志记录命令名、调用入口、执行结果、错误码和耗时，不记录完整参数和会话正文。
- 监控分别统计命令等待时间、实际执行时间、失败次数、超时次数和权限拒绝次数。
- 系统健康检查应确认命令目录已经成功加载；诊断命令只输出脱敏后的检查结果。
- 对命令持续失败、长时间等待、频繁超时和目录加载失败设置告警，并提供对应的处理说明。

五、业务安全设计

- 查询类命令只读取数据；修改模型、设置或 Session 的命令必须检查修改权限并记录审计日志。
- Session 切换、导入、压缩、退出等可能影响当前工作的命令，需要根据影响程度进行二次确认。
- 登录、退出和项目可信设置属于安全操作，应采用更严格的权限检查，凭证只能由认证组件保存和使用。
- 复制、导出和分享可能造成数据外泄，执行前需要检查数据权限，输出时过滤敏感内容，并记录外发审计。
- `/skill:<name>` 是动态 Skill 调用，不属于静态注册命令。它继续遵循 Skill 设计中的项目可信和加载规则；未知 Skill 按原文继续处理属于兼容性行为，需要作为安全风险记录。

六、性能设计

- 命令目录在启动时构建，执行时按命令名直接查找，不能每次都扫描全部命令。
- 输入补全读取已经加载的命令和 Skill 列表，用户每输入一个字符时不能重新扫描文件目录。
- 允许并行的只读命令可以同时执行；会修改共享状态的命令必须排队执行。
- 命令等待队列、输出大小、单用户调用频率和同时执行数量都应设置上限，防止一个用户占满系统资源。
- 网络、文件和其他下游调用需要设置超时，避免一个慢请求长期占用命令执行资源。
- 性能测试重点验证大量命令补全、多个用户同时调用、修改类命令排队和下游响应缓慢等场景。

七、验收要求

DFX 验收至少覆盖以下场景：

- 命令目录加载失败时，系统不提供不完整的命令列表。
- 聊天框、命令面板和按钮都不能绕过服务端权限和执行控制。
- 并发、取消、超时和下游故障后，系统仍能继续执行后续命令。
- 未授权用户不能读取或修改其他用户、租户或 Session 的数据。
- 日志、监控、错误提示和诊断输出不泄露敏感信息。
- 高并发和慢下游场景下，系统能够限流、排队或及时失败，不发生无限等待和资源耗尽。
