Slash Command DFX 分析概要

状态：待确认
适用设计：pi-mono Java Command SR 设计
建议位置：Command SR 第 14 节后新增“14.4 DFX 分析”

一、总体原则

- 所有聊天框、Command Palette 和按钮请求统一进入 Parser、Dispatcher 和 ExecutionGate。
- 命令目录、执行策略、权限、错误处理和观测保持统一，避免前端旁路和重复实现。
- 本 DFX 分析描述 Java 目标架构；取消、超时、并发和统一观测属于 Java 架构增强，不描述为 pi 已有能力。

二、可靠性分析（DFR）

- 启动时校验全部命令，成功后一次性发布不可变目录；失败时不发布部分目录。
- 通过 ExecutionGate 统一处理并发、取消、超时、运行时切换和关闭流程。
- Handler 异常、超时或取消后必须释放资源，迟到结果不得覆盖最终结果。
- 有副作用的命令由业务服务负责事务、幂等或补偿，避免重复执行。
- 重点验证启动失败、下游故障、Gate 卡住、运行时切换和优雅关闭。

三、安全检查（DFS）

- 前端不作为权限边界，所有入口都必须经过服务端目录、Parser、Dispatcher 和业务授权。
- 只允许执行可信目录中的命令；禁止未注册命令、参数注入和隐式 Shell 执行。
- 对命令输入、参数、输出和日志实施长度限制、敏感信息脱敏和资源消耗控制。
- 认证、Session、租户、项目和资源权限由服务端校验，不能依赖客户端传值。
- 通过安全测试验证越权、跨租户访问、伪造调用、敏感信息泄露和重复提交。

四、可服务性分析（DFO）

- 每次调用关联 correlation ID，记录命令名、入口、策略、结果、错误码和耗时。
- 分别观测排队、Handler、下游和总体耗时，指标标签不得包含原始参数或会话正文。
- Readiness 检查命令目录是否成功发布；/doctor 只提供脱敏诊断信息。
- 为命令忙、超时、失败、授权拒绝和目录安装失败建立告警和处理手册。
- 配置变更、命令版本和目录快照应可追踪，便于问题定位和回滚。

五、业务安全设计（DFB）

- 按只读、状态修改、Session 生命周期、认证安全、数据外发和应用关闭进行风险分级。
- 状态修改和 Session 切换使用权限校验、独占控制、状态一致性检查和审计。
- 登录、退出、信任设置、分享、导出和复制等高风险操作增加确认或更强认证。
- 审计记录主体、租户、Session、目标、结果和 correlation ID，不记录凭证和完整正文。
- `/skill:<name>` 继续遵循 Skill SR 的动态资源、项目可信和 fail-open 语义；fail-open 需记录为兼容性风险。

六、性能设计（DFP）

- 使用不可变目录和名称索引，保证命令查找不依赖全量扫描。
- Parser 按输入长度处理并限制输入大小；补全使用快照、去抖和请求序号。
- Skill 补全只在启动、Reload 或 Session 重新绑定时重建，不在每次键入时扫描资源。
- SHARED 与 EXCLUSIVE 命令分别控制并发；队列、输出、并发和单用户调用需要有界。
- 传递下游截止时间，分别统计解析、排队、执行和下游耗时，并通过压测验证并发行为。

七、DFX 闭环与验收

一次命令调用应形成“准入—执行—结果—恢复—观测”闭环：

1. 准入：身份、Session、权限、能力和执行策略检查。
2. 执行：统一 Gate 管理并发、取消、超时和生命周期。
3. 结果：返回统一状态、错误码、刷新提示和 correlation ID。
4. 恢复：失败或不确定结果不污染目录，副作用通过事务、幂等或补偿处理。
5. 观测：日志、指标和审计可支持定位问题且不泄露敏感数据。

验收至少覆盖：目录发布失败、路由旁路、权限拒绝、并发冲突、取消超时、下游故障、敏感信息脱敏、补全竞态和高并发执行。
