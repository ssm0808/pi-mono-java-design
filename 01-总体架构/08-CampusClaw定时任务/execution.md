## 业务主流程与异常边界

运营人员保存“每个工作日 08:00 汇总园区设备告警”后，Claw 在下一个有效计划时刻创建一次 Run 和一个独立 Session。Mate 维护用户、资源归属与当前授权，提供接口和执行凭据；Claw 仅保存资源关联及不透明 authorizationRef，不保存凭据引用，不保存用户范围或 owner。受理完成后由既有 Runtime 推进 Agent，完整对话及工具结果写入 Session。

错过的计划不补跑，上一次尚未结束时本次跳过，不堆积等待队列。失败只记录本次结果；不会因为失败、节点重启或回执丢失重新创建 Session、重发首条消息或者重放工具。下一次自然计划仍是独立的新触发，不属于重试；若前一次是否仍在执行尚不确定，则继续占用同一 Schedule，后续触发遇忙跳过。

删除 Schedule 同时删除其 Run，已经生成的 Session 保留。删除先于原子受理提交时阻止本次受理；受理先提交时既有 Session 继续由 Runtime 管理。删除后的回调只收尾原 Session/根执行，不复活 Schedule 或 Run。

## 无需人工交互的执行范围

首版定时执行仅支持无需人工交互的工作，仍按“可信目标解析→参数校验→权限判断→业务执行→结果回传”推进。框架默认不装配提问和计划审核工具；Host 还须识别业务权限 ASK、自定义问题准备结果及误配的交互工具，不能仅按工具名屏蔽。需要人工处理时，先阻止待确认业务调用，记录真实失败结果与原因，再结束本次根执行；不创建等待卡、不返回默认答案或批准，也不允许模型改名重试绕过。参数错误仍在权限判断前返回同次可信定义与 isError=true，保持既有修参规则。结束执行不回滚此前已发生的业务操作；可靠终态提交后释放任务占用。本次失败不自动重跑；是否改变 Schedule 状态另按配置生命周期规则确定。

非交互限制沿根执行传递到其Child执行，不能通过子会话或工具别名绕过。根执行结束应按既有取消域收尾已启动子任务；未确认终止的调用仍按停止中或未知处理，不把取消请求当成真实终态。

业务配置应只选择输入完整、权限已具备且无需人工决定的任务。这个条件不能仅靠提示词承诺；创建时可发现的明显不支持项应拒绝，运行时仍按可信能力和实际权限兜底。首版不新增持久等待检查点、交互恢复器或无人审批队列，普通交互Session已有确认和问答行为保持。

附件首版不支持：任务内容是纯文本prompt，无法携带文件，也不保存fileId。普通Session既有文件引用契约不受此限制；附件长期授权和跨Session复用留待M09单独实现。

## 模块与依赖方向

定时能力合并进 `modules/coding-agent-cli`，制品继续使用 `campusclaw-coding-agent`。根 Reactor 保留 common、ai、agent-core、coding-agent-cli 四个模块，不再发布独立 campusclaw-cron。定时任务仍是一项可单独阅读的设计职责，但不再拥有独立 Maven 制品或另一个服务进程。

| 位置 | 职责 |
|---|---|
| `codingagent.schedule` | Schedule/Run 应用规则、时间计算、受理准备、扫描派发、结果对账及数据库访问；按实际职责拆分 application、dispatch、persistence、config 子包 |
| `codingagent.tool.cron` | 将模型工具调用和当前 Agent、Session/执行及目标资源 ID 转换为相同应用服务请求，不保存另一份任务或调度状态 |
| `codingagent.runtimeapi` | HTTP Controller、请求/响应 VO 和既有 Runtime 受理边界；Controller 不直接使用 Mapper、调度线程或模型 |
| `codingagent.session` 与既有 Runtime | 公共 Session 创建、根执行、工具权限、终态与消息持久化；定时模块不重做 AgentLoop |
| `agent-core` / `ai` | 保持对宿主的单向依赖边界，不反向依赖 coding-agent 的定时或企业身份实现 |

管理及运行请求依赖 Schedule 应用服务；执行推进器独立消费受理状态并调用 Runtime。RuntimeSessionEngineRegistry 为交互会话装配 CronTool 时，只需要薄管理/受理服务，不注入调度推进器。不得形成 `Registry → CronToolFactory → ScheduleService → Dispatcher → Registry` 构造环，也不以 `@Lazy` 掩盖这个职责环。

当前独立 cron 有 15 个生产 Java 文件、7 个测试 Java 文件，无独立资源目录。合并时迁移相关源码和测试，删除根 POM 中模块条目、campusclaw-cron 版本管理项和 coding-agent 对其依赖；更新 `scripts/sync-campusclaw.sh` 的 MODULES、旧 CODEOWNERS 路径和工程文档，然后用同步脚本生成 corporate 包树，不双份手工维护。

旧 CronService 是自动启动的 SmartLifecycle。新 SQL 调度器启用前，必须停止旧 CronEngine 和 JSON/JSONL 写入，完成旧在途执行核对；不能让两套调度同时运行。现有 CronTool 和 BuiltInToolContracts 各有一份旧 at/every/cron Schema，工具迁移需同步处理，不将旧 at/every 数据静默转换成所谓等价 Cron。

本方案不新增外部依赖：复用 JDK21、Spring CronExpression、Jackson、MyBatis Spring Boot Starter3.0.4、既有数据库驱动。coding-agent 已直接依赖 agent-core、Jackson 和测试 Starter；Spring context 已经由既有依赖提供。如按“直接使用直接声明”原则补充 spring-context 声明，只调整已有依赖归属。根 POM 的 JobRunr7.3.1 目前只是无消费者的版本/管理占位，可在实施全仓复查后清理；不能据此宣称当前运行包体减少。完整依赖树及 corporate NativeParent 仍需实施时验证。

表职责、字段、约束、索引、删除与保留的数据库边界由 [Claw 数据库设计（定时增量）](../../03-数据与存储/Claw数据库设计.md#schedule)唯一维护。三张调度表及 Session/根执行扩展已在 PR #332 实现、未合并；完整源码基线、物理结构与目标差距见[数据库核验](../../03-数据与存储/Claw数据库设计.md#source-baseline)。本文继续维护业务受理顺序、恢复策略和部署参数，不复制字段字典或安装 SQL。

## 原子受理与同任务互斥

1. 自动扫描在短事务内锁定 Schedule，检查配置存在/active、计划时刻，以及该任务是否已有未完成 Run。忙时插入一条已结束（带 finished_at）的跳过结果并推进下一计划，不影响另一条未完成 Run。可受理时分配一次 Run，运行表部分唯一约束 `UNIQUE(schedule_id) WHERE finished_at IS NULL` 即本任务的占用；手动入口走相同互斥检查，但不修改自动游标。
2. 事务外向Mate查询可信接口和授权结果，并准备本次 Agent、模型和工作区快照。Claw 固定同次拟建 Session ID，由 Mate 独立登记归属并确认后才可受理；失败/未知处理见[Mate 会话归属](../../02-服务与接口/02-CampusMate共享客户端配置/scheduled-execution.md#session-ownership)。此阶段不得调用模型或业务工具，不持数据库行锁等待远端响应；附件不在首版输入范围。
3. 同库短事务内再次检查 Schedule/Run 的存在、状态、Agent 绑定是否与领取时一致、Run 未结束且 lease_until 未过、授权结果有效期、业务容量和自动派发期限；创建新 Session、首条用户消息（最新 prompt）、根 execution/segment，并写 Run 唯一关联。任何一步失败全部回滚，不能出现 Run 显示已受理但 Session/首消息缺失。
4. 提交后由持有本次准备快照的原实例使用一次启动 CAS 取得执行权，再调用 Runtime。受理回执不等待 Agent 完成；后台使用 persistenceOnly 输出路径，不伪造 SSE 浏览器连接。
5. 根执行是结果权威。Run/配置仍存续时，仅通过已关联的根 execution 幂等投影摘要并写入自己 Run 的 finished_at 以释放本任务；不存在则只收尾 Session 和内部状态。后续用户在同一 Session 发起的新对话不能改写原定时执行的结果。

自动运行的lastRunAt由原根执行持久化的实际开始时间投影，未开始的准备失败或跳过不更新；READY/STARTING的启动权标记不能单独证明实际开始。投影不修改配置updatedAt，手动运行不更新lastRunAt。

暂停、更新、删除与最终受理竞争同一个数据库权威；旧准备结果不得覆盖新配置。同一 Run 的重复内部通知只能读取其原关联，不能再创建 Session。对不同手动 HTTP 请求不自动合并，也不重新引入 If-Match、Idempotency-Key 或 ETag。

## 正常扫描迟到与不补漏跑

自动扫描使用数据库时间；所有副本都扫描、都可以承载 Runtime 执行，不选扫描领跑者，也不维护全局扫描代次或恢复边界。领取时以 `FOR UPDATE SKIP LOCKED` 锁定到期的 Schedule 行（GaussDB 支持须在实现时验证；不支持时退回 `FOR UPDATE`，只多等待锁），在锁内复核 upcoming_run_at 仍是本次计划时刻后推进游标；其他副本拿不到锁或看到游标已推进就跳过。`UNIQUE(schedule_id, scheduled_at)` 是最终防重。

扫描读取 upcoming_run_at 不晚于数据库当前时刻的 active 任务。计划08:00:00、正常轮询08:00:01才发现，仍在5秒派发容差内，可以受理；它属于同一次正常派发，不是补跑。机会若因繁忙、容量不足或权限失败而未受理，记录对应结果并前移游标，不再为同一 occurrence 入队或重试。

upcoming_run_at 早于数据库当前时刻超过派发容差时（停机、扫描停顿或数据库不可用后恢复），不运行、不记录 Run，直接把游标推进到当前时刻之后的下一次计划；不补最近一次，也不逐个补造历史计划。若数据库故障导致无法确认上次提交状态，恢复后先只读对账；不能以旧内存队列执行到期任务。

是否已提交 Run/受理以数据库为准；恢复后的副本不能删除或重发已受理的 Session。仍在准备中、从未受理且 lease_until 已过的 Run，由清理在锁内写入 finished_at 并记录本次未能受理，不由其他副本重新准备执行。其他副本接替的是未来调度，不是旧执行。

> 取舍：是否运行只看计划时刻与数据库当前时刻之差。延迟不超过5秒一律按正常派发处理、不区分原因，因此不超过5秒的短暂停机也会照常运行；超过5秒一律跳过。代价是每个副本每秒都扫描一次，查询量随副本数增加，扫描走 idx_schedule_due。

## 失败、失联及未知结果

| 观察到的事实 | 本次处理 | 后续自然计划 |
|---|---|---|
| 明确未受理且准备/凭据/容量失败 | 记录未受理结果，不重试本次，不创建 Session | Schedule仍为active时按下一计划尝试 |
| 已经受理、可以证明尚未取得启动权，且原拥有者已被持久 fencing | 通过 CAS 结束未启动状态，记录未能启动；不转交新节点执行 | 释放本任务后，active任务按下一计划尝试 |
| 已取得启动权后失联、回执丢失或工具结果不明 | 保留“结果未知/待对账”，不伪造成功或失败，不重发首消息或工具 | 同一任务保持占用，后续遇忙跳过 |
| 根执行明确成功/失败/取消 | 保存真实终态并释放本任务；不因失败启动另一次执行 | active任务按下一计划尝试 |
| 对账时 Schedule/Run 已被删除 | 只完成原 Session/根执行和必要内部收尾 | 已无该 Schedule 的后续计划 |

同次失败与故障不重跑已确认。是否自动暂停整个Schedule仍待明确；本页不继承旧Cron连续失败自动禁用的策略，status转换须在该决策明确后实施。不重跑不等于不对账：只读查询已有结果、幂等落地已确认终态、清理已结束资源可以继续重试，它们不调用模型或产生新的园区业务请求。

未知执行不得因为固定租约到期就写入 Run.finished_at；必须取得根执行终态、可靠未启动证据，或经过独立授权的人工处置才解除占用。若根执行现有枚举不包含“未知”，定时内部协调保存 unknown 并在运营视图明确标注，不能把公开 Run 的 admission error 冒充 Session 业务终态。

## 首版部署初始值

下列默认值由部署配置控制，不新增 Schedule 公共字段。它们用于限制首次上线风险，扩容前仍需测试；用户保留的 Spring 六字段能力包含秒位，但每秒表达式不等于每秒均能成功受理。

| 配置 | 初始值 | 语义 |
|---|---:|---|
| 自动扫描周期 | 1秒 | 正常期望扫描频率，不是精确启动承诺 |
| 自动派发容差 | 5秒 | 计划时刻与数据库当前时刻之差的上限；超限不运行、不排队、不补跑，游标推进到下一次 |
| 扫描批量 | 100条 | upcoming_run_at/id 有序、有界扫描；Claw 不按用户/租户分组，跨租户公平策略归 Mate |
| 每任务并发 | 1 | 自动和手动共享；结果未知也占用 |
| Cron时间分辨率 | 1秒 | 沿用六字段能力；派发和执行受批量、迟到及并发配额约束，不承诺每秒任务均有容量 |
| Mate 每管理范围任务数 | 100个 | 由 Mate 的任务关联和配额准入维护；Claw 不做 countScope，不持久化范围；Mate 配额与任务创建失败对账待实现 |
| 每实例定时活动执行上限 | 8个 | 独立调度配额，且必须同时取得既有Runtime容量；不能绕过交互任务容量保护 |
| 受理准备期限 | 10秒 | Mate/目录准备超时只记本次失败；自动受理仍须满足5秒派发期限，取更早者 |
| 单次运行上限 | 30分钟 | 到期向原根执行请求停止；停止未确认仍保持运行中/停止中或未知，不能强制改成已终止 |
| 存续Schedule的Run保留 | 30天 | 仅清理已明确结束的历史；未知和内部协调不因到期直接删除；删除Schedule仍立即删除对应Run |
| 清理频率 / 批量 | 每小时 / 500条 | 有界删除；不得级联Session或正在协调的根执行 |

首次上线不承诺一个未经测试的集群总并发数。多副本扩容后，每实例8个上限会放大总并发，应在部署阶段按实例数和下游配额核对。若必须提供全局或租户执行并发硬上限，应复用Runtime已有权威准入；没有现成能力时新增一致性设计和验收，不能用各实例内存计数器冒充集群限流。

Run保留策略不决定Session的保留期限。Session继续归所属模块策略管理，不能因为运行超过30天而自动清除对话。

## 实施和验收

1. 先迁移物理模块与包，核验旧模块/GAV引用清零、Spring构造无环、corporate镜像布局一致；不以搬包替代新运行能力。
2. 实现 Schedule/Run 和同库原子受理，完成2副本并发、唯一发生时刻、更新/暂停/删除与受理竞态验证。
3. 接入Mate可信接口和凭据、公共Runtime执行及完整事件；首版拒绝附件和需要交互的任务路径，不自动批准业务操作。
4. 用可控时钟验证：08:00:01正常轮询可受理；08:00:06发现08:00:00的计划时跳过；超过容差跳过；忙时不排队；DST缺失时刻跳过，重复钟面按不同UTC occurrence处理。
5. 注入准备前/提交前/提交后/启动CAS前后/业务调用后的故障，确认无重复Session、无重复首消息、未知不伪失败、重启不重放；旧拥有者被fencing后不能再次提交。
6. 验证删除后所有Schedule/Run查询不可见，Mate 中原 Session 归属仍在且可按当前权限读取，晚到回调不复活资源；确认Run清理不删除Session。
7. 执行reactor verify、镜像布局、GaussDB集成及2副本联调；按默认配额测试数据库延迟、扫描容差、下游限制和交互任务资源竞争，再决定是否提高初始值。没有真实压测结果前不写“支持多少任务/并发”的容量承诺。

## 与基线的差异与代价

Claude公开API仍是配置、Run与Session职责划分的历史主基线，事实归属与成熟度见源码证据。本页的无补跑、不重跑、非交互入口、Mate权威与模块合并是CampusClaw已选产品约束和架构变更，不是新增上游实现结论。自动扫描由各副本并行进行、以行锁和唯一约束防重，不维护全局扫描代次，代价是查询量随副本数增加；执行同样分布式。严格不重跑避免重复业务操作，代价是进程故障可能漏执行，未知状态需要对账或人工处置。
